# Swift seam map (SW3)

What each wire-using function in the Swift app (`apps/apple`) becomes when it runs over the Rust core, which
core methods are missing, and the threading and mirror rules that SW4-SW14 follow. SW3 in
`docs/core-merge/PLAN-CLIENTS.md` section 5.4. Checked against `main` at `9620d21f`.

**Path conventions.** Swift paths are relative to `apps/apple/DSPi Console/`. Rust paths without a directory
are relative to `crates/dspi-core/src/`. "Binding line" is the line of that method's declaration in
`DspiCoreProtocol`, in `ci/generated/swift/dspi_core.swift` (generated by UniFFI through `crates/dspi-ffi`).
`DSPi Console/Core/Generated/Sources/dspi_core/dspi_core.swift` is byte-identical to it (`diff -q`, SW2). `S.x` means
field `x` of `DspState` (`records.rs:220`), read with `getState()` (`connect.rs:233`, binding `2170`).

**How the inventory was made.** A script lists every Swift function that calls `sendControlRequest`,
`getControlRequest`, `getControlResult`, `addNotificationObserver`, `acquireDeviceLock`, `releaseDeviceLock`,
`withDeviceLock` or `markDisconnected`. That gives 310 (file, function) pairs. Of these, 256 are command functions,
mapped in section 3. The other 54 are the `DeviceTransport` implementations, mapped in section 4. The core
side is the 204 methods of `DspiCoreProtocol` (binding lines 1237-3540), the free functions, and the listener
protocols. Every core method named in section 3 exists, and its Rust `pub fn` line is given. The script is in
`~/.cache/dspi-build/work/wp-SW3/tools/` (`inv2.py`, `map.py`, `gen.py`).

## 1. Summary

- **Of the 256 command functions, 252 have a core method today.** The other four, all of them lock holders, need **CG24**:
  - `csIrLearnArm` and `csIrLearnEnd` (`Commands.swift:3527`, `:3562`);
  - `enterBootloaderForInstall` and `releaseFirmwareInstallLock` (`Commands.swift:3575`, `:3590`).
- **Two functions have no caller and are deleted, not mapped:** `fetchSavedMasterVolume` (`Commands.swift:806`)
  and `RtaEngine.resetAveraging` (`SpectrumAnalyser.swift:597`). `grep` finds only their declarations.
- **Every `fetch*` that reads one setting becomes a `DspState` field.** That is 77 of the 256 rows. Every
  property that Swift's bulk decoder writes (`Commands.swift:3714-4223`) has a `DspState` field. The
  `*Supported` gates come from `wireFeatures()` (`device.rs:466`, binding `3538`). So the 517-line decoder is
  deleted, not ported.
- **The transport layer needs three core WPs,** proposed in section 6:
  - **CG23**, a raw notification tap with the connection id, for SW4;
  - **CG24**, a device lock held across a flow;
  - **CG26**, a host-supplied transport, for SW4's byte-level tests and for the Mac's local path until SW-M3.
- **The notification events need one core WP,** also in section 6: **CG25** adds stream-state events, which the
  core drops today (`notify.rs:422-427`).
- **One decision needs the coordinator** (section 5.4): how the Mac reaches its local USB device before SW-M3.
  The recommendation is CG26, which keeps the plan's order.
- **Re-sizes** are in section 7. SW8-SW14 go from 12-21 to 14.5-17.5. The four proposed core WPs add 2.

## 2. The seam today

`DeviceTransport` (`Link/DeviceTransport.swift:131-179`) is the one protocol that the view model and the tool
windows use. It has:
- two transfer calls: `sendControlRequest`, fire-and-forget (`:160`), and `getControlResult`, blocking (`:167`);
- a notification stream (`:171`);
- the device lock (`:177-178`);
- connection and selection state (`:133-157`).

Every implementation sends SETs **asynchronously on a private serial queue** and runs GETs **synchronously on the
same queue**, so a GET sees every earlier SET:

| Implementation | SET | GET |
|---|---|---|
| `USBDevice` | `serialQueue.async` (`USBDevice.swift:613`) | `serialQueue.sync` (`:675`) |
| `MIDITransport` | `requestQueue.async` (`MIDI/MIDITransport.swift:346`) | `requestQueue.sync` (`:372`) |
| `HubTransport` | `hub.submit` (`Link/HubTransport.swift:77-83`) | blocks on the hub's completion (`:85-109`) |
| `NetworkTransport` | `client.command` (`Link/NetworkTransport.swift:339-346`) | blocks on the reply (`:348-378`) |

Which transport the UI drives (`DSPi_ConsoleApp.swift`, `AppState`):
- **macOS:** `CompositeTransport`. Its local member is `HubTransport`, session 1 on the in-process Swift hub, which
  owns `USBDevice`. Its remote members are one `NetworkTransport` per discovered hub
  (`Link/CompositeTransport.swift:17`, `remotes` by hub id).
- **macOS with `-LocalTransport midi`:** `MIDITransport` is the local member.
- **The iOS target:** the local member is a `LocalTransportSet` of `MIDITransport` and `FakeTransport`
  (`DSPi_ConsoleApp.swift:107-108`).
- **`-LocalTransport demo`:** `FakeTransport`.

The 256 command functions are spread as follows:
- 233 in `Commands.swift`, which has 4 929 lines and 49 `MARK` sections;
- 4 in `ExtensionCommands.swift`;
- 11 in `StatsView.swift`;
- 6 in `SpectrumAnalyser.swift`;
- 1 each in `InterruptMonitor.swift`, `PresetDocumentTransfer.swift` and `FirmwareUpdateView.swift`.

The plan counts "wire references" for `DSPi_ConsoleApp` (29), `ContentView` (14) and `TestSignalsView` (18).
Those references are not transfers. They are `transport.generation` guards around calls into the view model,
as at `DSPi_ConsoleApp.swift:1476-1481`, `ContentView.swift:107-109` and `TestSignalsView.swift:1058-1060`. They
stay, and section 5.3 gives `generation` an exact meaning.

## 3. Command functions: each one mapped to a core method

Each table holds the functions that one WP removes. The **Wire use today** column gives the opcodes, with
`REQ_` dropped and `wValue` after `/`. **Core replacement** names the binding method, or `S.field` for a
mirror read. "Re-reads" names the call to use when a fresh value is needed outside a notification. "Coalescing
write lane" is section 5.2. A **gap** names the proposed core WP in section 6.

Assignment choices that the plan's domain list left open:
- LG Sound Sync and the DAC hardware mute go to SW11, as hardware and input settings.
- Master-volume mode and output-config mode go to SW13, because they are preset-directory flags
  (`Commands.swift:767`, `:4490`).
- The leveller and the limiter go to SW10, as effects.
- Core 1 mode and output latency go to SW9, as outputs.
- `fetchStatus` and the clip and sample-rate polls go to SW14, as status.

### 4.3 Several hubs, one core

Today `CompositeTransport` keeps a live session to every remote hub, only to list each hub's devices. A
`DspiCore` holds one connection.

- local devices from `scanDevices()`;
- each browsed hub's `LinkInfo.serials` from `linkFetchInfo` (`records.rs:931`), fetched on `coreQueue` when
  Bonjour reports a change and while the picker is open.

names before binding, adding them to `/dspi/v1/info` is a spec and hub change. That is not proposed here; SW6
records it as a risk.

## 5. Threads and the mirror

### 5.1 Queues

**No core call runs on the main thread, not even the getters.** These take the core lock:
- `getState` (`connect.rs:233-234`);
- `rtaGetSnapshot` (`rta.rs:163-164`);
- `isConnected` (`device.rs:441-442`);
- `linkStatus` (`link.rs:533-534`).

`fetchAll` holds that lock "for the whole read: a few hundred milliseconds over USB, seconds over MIDI or a slow
Link" (`connect.rs:95-99`). So a getter on main would freeze the UI behind any transfer.
`crates/dspi-ffi/src/lib.rs:21-28` states the same rule for bindings.

| Queue | Owner | Runs | Never |
|---|---|---|---|
| `coreQueue`: serial, `.userInitiated`, label `com.dspi.core` | `CoreBackedTransport` and, after the domain moves, `CoreClient` | every core call, in submission order. SETs go `async` and GETs go `sync`, as every transport does today (section 2). Also `processNotifications` + `getState`, `pollHotplug`, `linkFetchInfo` | blocks on main with `.sync` |
| main | SwiftUI and `DSPViewModel` | applies `DspState` and `NotifyResult` to `@Published` (section 5.2), and the `NotificationFanout` handlers | any core call. A debug assertion in `CoreBackedTransport` catches one |
| core threads: notification reader, RTA worker, Link supervisor | the core | the listener callbacks | blocking work, or calling `set_*_listener` (it self-deadlocks: section 1 rule, `callbacks.rs:1-12`) |

Callers keep their existing queues: `pollQueue` (`DSPViewModel.swift:2542`), Stats' `fetchQueue`
(`StatsView.swift:319`), `DispatchQueue.global`. They call into `coreQueue.sync`, which is no worse than today's
`serialQueue.sync`.

**SW4 parity rule for GETs from main.** A GET called from main still works, with `coreQueue.sync` exactly as
`USBDevice` does today, and is logged in debug builds. Each domain WP's done criterion includes "no GET from main
in this domain".

`coreQueue` never calls `DispatchQueue.main.sync`, so main calling `coreQueue.sync` cannot deadlock.

**Listener hops.** A listener only schedules work. Each one:
- `NotifyListener.onNotifications` (`callbacks.rs:18-22`): sets a flag. At most one `coreQueue` job per 30 ms (the
  core's stated batching) runs `processNotifications()`. For SW4 it also drains the tap (CG23). Then it posts to main;
- `RtaListener.onFrame`: schedules a `coreQueue` job for `rtaGetSnapshot()`, coalesced to the display rate, which hands
  the snapshot to the Metal renderers on main;
- `DeviceEvents` and `LinkListener`: schedule state refreshes on `coreQueue`.

**Hot-plug.**
- macOS (SW-M1): `pollHotplug()` on `coreQueue` from a 1 s timer, because the core's `usb` feature does the bus
  scan. `poll_hotplug` can block for a whole reconnect (`crates/dspi-ffi/src/lib.rs:22-24`).
- iOS has no USB in the core (CG3). CoreMIDI endpoint changes (`MIDIControlPort.swift:124-138`) trigger
  `scanDevices` on `coreQueue`.

### 5.2 Which state is mirrored, and where

**Two copies, one owner each.** The core's `DspState` is the device's state as last confirmed. Swift's `@Published`
values are what the UI shows. They may run ahead of the device while an edit is in flight. Typed setters update
`DspState` at once (`params.rs:326-330`, `set_scalar`). The core patches its mirror from every `PARAM_CHANGED`,
our own echoes included, and flags only a real change (`notify.rs:345-358`).

| Swift state | Source | Applied |
|---|---|---|
| Every setting `@Published` (the 126 property paths written at `Commands.swift:3714-4223`: EQ, crossover, preamps, volumes, effects, matrix, outputs, pins, I2S, ADAT, inputs, names, presets) | `getState()` after a `NotifyResult` with `NOTIFY_STATE`, `NOTIFY_REFRESHED`, `NOTIFY_PRESET` or `NOTIFY_NAMES`, and after `fetchAll`/`refreshParams` | On main, by a single `CoreMirror.apply(old:new:)` (SW8) that writes only the fields whose **core** value changed between the two snapshots, and skips pending keys (below) |
| `*Supported` gates (`adatSupported`, `i2sClockModeSupported`, `lgSoundSyncSupported`, `firmwareSupportsCrossover`, …) | `wireFeatures()` and `S.format_version`, `S.compat` | On connect and on `NOTIFY_REFRESHED` |
| Read-only mode (older firmware) | `S.compat`, `S.bulk_valid`. Setters return `ReadOnly` (`connect.rs:75-80`) | Shown by SW8. Controls disabled |
| Meters, CPU, clips, active inputs | `fetchStatus()` → `SystemStatus` with `stale`, `age_ms` | Polled on `coreQueue` at today's rate. Posted to `meters.status` on main |
| Signal generator, ADAT/I2S/ADAT-in lock status, LG status, upmix status, limiter and subharm meters, ring health, buffer stats | The `fetch*` status calls in section 3 (SW14, SW10, SW11) | Polled, or on their flags: `NOTIFY_SIGGEN` and CG25's flag |
| Control surfaces | `csSnapshot()` JSON, plus `NOTIFY_CS_AUX`, `NOTIFY_IR_LEARN` | A CS store on main, refreshed from `coreQueue` (SW12) |
| Analyser | `rtaGetSnapshot()`, `rtaGetOwnership()` (CG5's following state) | Through `RtaListener` (section 5.1) |
| Link phase, reconnect countdown | `linkStatus()`, `linkPhaseText` | On `onLinkStatusChanged`. Banner by SW7 |
| Unsaved-changes baseline | `presetDirty()`, `presetChanges()`, `captureBaseline()` | Replaces `savedSnapshot` with `PresetSnapshot` in SW13 |
| UI-only state: visibility, selection, drafts, input-pair link mask, window state | Swift | Never mirrored |

**Echo flicker rule: pending keys.** A setter registers its `DspState` key (for example `filters[3][2]` or
`master_volume_db`) with the value sent. `CoreMirror` skips a pending key until one of these happens:
- the core reports that same value;
- 500 ms pass after the last write to that key;
- `generation` changes.

This replaces today's drop-own-echo rule (`DSPViewModel.swift:2669-2680`). That rule is needed only while
`CoreBackedTransport` sends raw writes, whose echoes do change the core's mirror (`raw.rs:43-47`). It stays
harmless after the domains move. SW8's test for "no echo flicker" drags a value on the demo device while echoes
arrive late.

**As built (SW8, `Core/CoreMirror.swift`).**
- A field is pending from the moment its `@Published` value changes outside `CoreMirror.apply`. The mirror watches
  each mirrored property's publisher, so setters register nothing by hand, and a domain WP that moves a setter to
  the typed API keeps the rule for free. EQ, crossover and channel names have one key per wire channel.
- A field held back by a pending edit is applied 500 ms after the last edit if the core still differs (one sweep).
- `NOTIFY_REFRESHED` applies the whole state over pending edits, and so does a `BULK_INVALIDATED`, which is
  RefusedWrite's revert. A `NOTIFY_PRESET` then rebases the unsaved-changes snapshot on that refresh.
  -- WP SWF6 -- Superseded: through the core, the unsaved-changes flag and the prompt's list are the core's
  (`presetChanges`, CG7), delivered with each `CoreStateChange` and after a fetch, a load and a save
  (`DSPViewModel.corePresetChanges`). The core rebases at the load's re-read and keeps an edit made after the load
  unsaved (CG33). A load goes through the core's `loadPreset`; a raw save is followed by `captureBaseline` (after a
  drain, so the last edits' echoes are in it). The Swift `PresetSnapshot` serves only the transports not yet on the
  core (USB without `-CoreTransport`, MIDI, the Link client) and a view model not connected through one.
- `DspState` has no field for four +1-encoded presence bytes: I2S clock-pin mode, the S/PDIF 2-4 mask, and ADAT-in
  enable and clock mode. The mirror reads them from `bulk_raw`, a CG candidate.
- The transports not yet on the core (USB without `-CoreTransport`, MIDI, the Link client) keep the Swift decoder
  until SW-M1, SW5 and SW6.

**Slider fast path** (`Commands.swift:257-345`, `ContentView.swift:1464`). The `send*ToDevice` functions become
typed setters behind a coalescing write lane on `coreQueue`. While a write for key K is still queued, a newer
value for K replaces it, so a drag sends at most one write per transfer time. The lane drops every queued write in
four cases:
- `generation` changes;
- `isConnected` goes false;
- `linkStatus().phase` leaves `Bound`;
- a write fails.

**Writes are never replayed** (owner's Link rule, PLAN-CLIENTS section 1). Release commits the last value with the
ordinary setter. SW9 owns it.

**Resync.** `scheduleDeviceResync` (`DSPViewModel.swift:2592`) and its coalescing are replaced by the core's own
re-read, which `NOTIFY_REFRESHED` reports. A preset load's re-baseline is `loadPreset` doing `captureBaseline`
(`presets.rs:111-128`).

### 5.3 `generation`

`DeviceTransport.generation` guards are used in 5 files, in the pattern at `ContentView.swift:107-109`. They keep
their meaning, "the connection this work was issued for". The value is the core's connection generation
(`lib.rs:231-234`), exported by CG23. It changes on:
- every open and close;
- a Link re-bind after a reconnect.

Until CG23 lands, SW4 counts its own opens, closes and `onLinkStatusChanged` re-binds. That is exact for
everything the app initiates, and misses only a core-internal reopen.

### 5.4 Decision for the coordinator: the Mac's local device before SW-M3

On macOS the in-process Swift hub owns the USB device (`HubTransport` over `LinkHub` over `USBDevice`).
Remote consoles share it through `LinkServer`. After SW9, the domains call typed core methods, so **the core must
hold the Mac's local connection before the first domain WP merges.** Otherwise those methods find no
device and the Mac's USB path breaks. iOS is unaffected: MIDI (SW5), demo, Link (SW6).

| Option | Cost | Risk |
|---|---|---|
| **A: CG26, host-supplied transport (recommended).** The core runs over the Swift `HubTransport`, through a UniFFI foreign trait around the existing `open_transport(Box<dyn Transport>)` (`device.rs:451-457`) | CG26 0.75. Throwaway at SW-M3: about 0.5 of Swift glue | Small. The Swift hub keeps working unchanged. The same trait also lets SW4 run the existing byte-level tests through Swift's `FakeTransport` |
| B: pull SW-M1 and SW-M3 ahead of SW9 (core owns USB through `nusb`; Rust hub with `attach_app`) | 2-3.5, needed anyway | SW-M3 depends on HB7 (TODO, [HW]), and `nusb`'s `macos_iokit` has never run on real Apple hardware (SW-M5). Both land on the critical path of all six domain WPs |
| C: the Mac's core connects over Link to its own Swift hub on loopback | Swift only, about 1 | Needs `LinkServer` listening even with sharing off, and a self-issued token. The lost-connection banner would show for loopback. Exercises an untested Swift-hub/Rust-client path that HB7 is meant to prove |

Option A changes no public contract. It adds a binding, so it needs the coordinator's agreement, not the
owner's.

## 6. Proposed core WPs

These are numbered after CG22, the last core WP in PLAN-CLIENTS section 4.1. Each one is small and in the
style of CG4. All are exported to UniFFI and the C ABI, and the Android contract is regenerated.

**CG23: Raw notification tap and connection generation.** Size 0.5.
- **Owns:** `crates/dspi-core/src/raw.rs`, extended; one recording line in `notify.rs` beside `inner.monitor.record` (`notify.rs:326`).
- **Implements:**
  - `notify_tap_set(enabled)` and `notify_tap_drain() -> Vec<RawNotification>`. A `RawNotification` holds `packet`, `origin`, `own` (the echo filter's verdict, `notify.rs:327`) and `received_ms`. Entries are recorded when `process_notifications` drains, so the mirror and the tap see the same order. The ring is bounded (512) and sets `lost` on overflow. The tap is off by default and costs nothing when off.
  - `connection_generation() -> u64`, from `Inner`'s `generation` (`lib.rs:234`).
- **Why:** `CoreBackedTransport.addNotificationObserver` must hand `InterruptMonitor` and every `onX` callback
  (`DSPViewModel.swift:2669-2810`) the verbatim v2 packet with its origin. `NotifyResult` (`records.rs:461`)
  carries only flags.
- **Retires** when SW14 moves `InterruptMonitor` to `monitorRead`. SW-M4's audit removes it.
- **Done when:**
  - On `FakeDevice`, our own write's echo has `own = true` and a foreign source (GPIO) has `own = false`.
  - A fake-hub test gives another session's origin.
  - Overflow sets `lost`.
  - The generation changes on reopen and on a Link re-bind, and never repeats.
- **Deps:** CG4.

**CG24: A device lock held across a flow.** Size 0.5.
- **Owns:** the lock section of `crates/dspi-core/src/presets.rs` (`:363-430`); `learnArm`, `learnRead` and `learnCancel` in `cs.rs`; `enter_bootloader` (`hardware.rs:883`).
- **Implements:**
  - `device_lock_acquire(reason, timeout_ms) -> Result<()>` and `device_lock_release()`, with Swift's semantics (`Link/DeviceTransport.swift:173-178`). The lock is held in `Inner` and checked against the connection generation. The core's own locked flows nest inside a held lock without asking the hub again. On USB, MIDI and the demo device it succeeds at once, as today.
  - `learnArm` takes the lock for the learn window, 15 s (`Commands.swift:3540`). A final `learnRead`, `learnCancel` or the timeout releases it.
  - `enter_bootloader` takes it. The hub drops it when the device leaves.
- **Why:** these four functions have no core path:
  - `csIrLearnArm`, `csIrLearnEnd` (`Commands.swift:3527`, `:3562`);
  - `enterBootloaderForInstall`, `releaseFirmwareInstallLock` (`:3575`, `:3590`).
  Until the domains move, Swift's composite flows sent as raw commands over a core Link connection need the
  generic call too. Without it, `CoreBackedTransport` could only return the protocol's default `true`, which is
  unlocked on Link. The same gap affects Qt and Android's firmware updaters (QD11, AN18).
- **Done when:**
  - In a fake-hub test, another session's write gets `Locked` during a learn window and during the bootloader restart.
  - The lock is released on each of the three exits and on disconnect.
  - A nested `save_preset` under a held lock does not deadlock.
  - The lock is never held after its connection changes.
- **Deps:** CG20.

**CG25: Stream-state events in `NotifyResult`.** Size 0.25.
- **Owns:** `crates/dspi-core/src/notify.rs` (`:422-427`), one flag in `consts.rs`.
- **Implements:**
  - `NOTIFY_STREAMS` (bit 11) for `AdatState`, `I2sSlaveState` and `AdatInputState`, which the session already decodes and the core drops.
  - The mirror follows `ADAT_STATE`'s `enabled` and `pin` into `S.adat_out_enabled` and `S.adat_out_pin`, as Swift does at `DSPViewModel.swift:2732-2744`.
  - A client re-reads `fetchAdatOutStatus` or `fetchInputLock(0|1)` on the flag.
- **Why:** the Mac follows these pushes live, through `onAdatState`, `onI2sSlaveState` and `onAdatInputState`
  (`DSPViewModel.swift:2732-2767`). The Mac is the feature floor.
- **Done when:** each event on `FakeDevice` sets the flag. The ADAT fields follow. Qt and Android are unchanged:
  a new bit they ignore.
- **Deps:** `main`.

**CG26: Host-supplied transport.** Size 0.75.
- **Owns:** a new `crates/dspi-core/src/host_transport.rs`.
- **Implements:**
  - A UniFFI foreign trait `HostTransport`, with `control_in(opcode, value, len)`, `control_out(opcode, value, data)` and `kind`, adapted to `dspi_transport::Transport`.
  - `open_host(transport, serial)`, through the existing `open_transport` (`device.rs:451`).
  - `host_notify(packet, origin)` to feed that connection's notification reader.
  - Calls into the trait come on `coreQueue`'s thread, under the rule for every foreign callback: must not block for long.
- **Why:**
  - It lets the Mac's core reach the local device through the Swift hub's session 1 until SW-M3 (section 5.4, option A).
  - It lets SW4 meet its done criterion, "existing `FakeTransportTests` and wire tests pass", with the Swift `FakeTransport` still recording the bytes underneath.
- **Retires** at SW-M3, and when the last domain WP has ported its byte tests.
- **Done when:** a scripted host transport gives the same `fetch_all` mirror as `FakeDevice`. Writes go out in
  order. Notifications reach the mirror. A transport that errors or hangs ends in `Disconnected` or `Transfer`,
  never a panic.
- **Deps:** CG23.

**What these change in the existing entries.**
- SW4's deps become SW3, CG4, CG23, CG26.

- SW12 and SW-M2 add CG24.
